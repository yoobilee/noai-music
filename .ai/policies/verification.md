# 변경 위험도와 검증 정책

## 목적

기계적 검증을 기본 방어선으로 사용하고, 변경 위험도에 따라 테스트, Codex self-review와 사람 확인의 강도를 조절한다.

## 위험도 분류

| 등급 | 대표 예시 | 최소 검증 | 병합 확인 |
|---|---|---|---|
| 낮음 | 문구, 주석, CSS, 단순 UI, 비기능 문서 | 관련 Lint·Build·화면 확인, self-review, 구성된 CI | 정책 조건 충족 시 auto-merge 가능 |
| 중간 | 일반 기능, API, 상태 처리, 보통 규모 리팩터링 | 전체 Lint·Test·Build, self-review, CI | 위험 조건이 없을 때만 auto-merge 가능 |
| 높음 | 인증·권한, 확장 프로그램 권한, 보안, 결제, 개인정보, DB 구조, 핵심 로직, 대규모 리팩터링, CI/CD | 전체 검증, self-review, 회귀·실패·롤백 경로, CI | 사람 확인 필수, auto-merge 금지 |

다음 조건은 위험도를 한 단계 높인다.

- 데이터 손실이나 권한 상승 가능성
- 공개 API 또는 저장 형식의 호환성 변경
- 테스트가 부족한 오래된 영역
- 여러 서비스나 패키지에 걸친 변경
- 변경 범위를 충분히 설명하기 어려움
- `.github/workflows/` 등 자동화 자체의 변경

## 테스트 도입

- 문구와 정적 시안 중심 초기에는 Test 도구를 강제하지 않고 Lint, Build와 화면 확인부터 구성한다.
- 상태, 계산, API와 데이터 저장처럼 검증 가능한 로직이 생기면 생태계의 일반적인 Test 도구를 도입한다.
- 일반 기능은 핵심 정상 동작을 검증한다.
- 버그 수정은 가능한 경우 회귀 테스트를 추가한다.
- API·DB 연동은 정상 흐름과 대표 실패 상황을 검증한다.
- 인증·권한·결제·개인정보·DB 구조·핵심 로직은 정상·실패·권한 경계를 검증한다.
- 핵심 사용자 흐름에는 필요한 최소 수의 통합 또는 E2E 테스트를 둔다.
- 초기에는 전체 코드 커버리지 비율을 강제하지 않는다. 필요가 생기면 핵심 모듈 또는 기존 수준 하락 방지 기준을 프로젝트별로 정한다.

## 호환성·반응형·접근성

- 프로젝트별 지원 기기·브라우저에서 핵심 흐름을 확인한다.
- 브라우저 확장 프로그램은 manifest 권한, content script 실행 범위, 대상 사이트의 SPA 전환과 동적 DOM 변경을 확인한다.
- 모바일·태블릿·데스크톱에서 내용 잘림, 가로 넘침, 조작 불가와 레이아웃 붕괴를 확인한다.
- 시맨틱 HTML과 표준 기능을 우선한다.
- 키보드만으로 주요 기능을 사용할 수 있는지, 초점이 보이는지 확인한다.
- 폼 레이블, 이미지 대체 텍스트, 명도 대비와 화면 확대 사용성을 확인한다.
- 자동 접근성 검사는 보조 수단이며 수동 확인을 완전히 대체하지 않는다.

## 완료 선언 전 최신 검증

- 완료, 해결 또는 통과를 보고하기 직전에 현재 변경이 포함된 상태에서 해당 주장을 증명하는 검증을 새로 실행한다.
- 이전 실행 결과, 일부 검사 결과, 다른 실행의 완료 보고와 “통과할 것”이라는 추측을 완료 근거로 사용하지 않는다.
- 실행한 명령의 전체 결과와 종료 코드, 실패 개수를 확인한 뒤 실제 결과만 보고한다.
- 일부 검사만 실행했다면 전체 검증이 끝난 것처럼 표현하지 않는다.
- 버그 수정 완료는 기존 증상이 해결됐고 가능한 경우 추가한 회귀 테스트가 수정 전에는 실패하고 수정 후에는 통과하는지 확인한 뒤 보고한다.
- 검증을 실행할 수 없거나 실패했다면 이유와 남은 위험을 밝히고 통과했다고 표현하지 않는다.
- 리뷰 대상 커밋과 현재 PR의 최신 커밋이 일치하는지 확인한다. 필수 CI도 현재 병합 대상 변경을 검증한 결과여야 한다. 코드나 병합 기준이 바뀌면 영향을 받는 검증을 다시 수행한다.
- 로컬 완료 보고와 원격 반영 여부를 구분한다. push했다고 보고하기 전에는 로컬 HEAD와 해당 원격 브랜치의 커밋이 일치하는지 별도로 조회한다.

## 간헐적 실패와 백로그

- 안전성·보안성에 영향이 없고 현재 작업을 막을 정도가 아닌 간헐적·사소한 문제는 백로그로 이관할 수 있다.
- 기존 이슈 도구가 있으면 그곳을 사용하고, 없으면 첫 항목이 생길 때 `.ai/BACKLOG.md`를 만든다.
- 증상, 재현 조건·빈도, 영향, 로그, 시도한 해결과 다음 조치를 기록한다.
- PR에서 발견한 문제라면 PR 설명에 백로그 항목과 이관 이유를 남긴다.
- 반복 실행으로 우연히 통과한 결과만으로 해결 처리하지 않는다.
- 현재 변경과 무관하고 위험이 낮은 간헐적 테스트는 근거와 백로그를 남겨 비차단 검사로 격리할 수 있으나 조용히 건너뛰거나 삭제하지 않는다.
- 필수 CI 실패, 회귀, 보안·결제·개인정보·데이터 손상과 핵심 로직 문제는 백로그 이관만으로 병합하지 않는다.

## CI 계약

1. 로컬과 CI가 가능한 한 같은 전체 검증 진입점을 사용한다.
2. 잠금 파일을 기준으로 의존성을 재현 가능하게 설치한다.
3. 구성된 Lint, Type Check, Test와 Build를 명시적으로 실행한다.
4. 검사가 없거나 구성되지 않았다면 조용히 성공시키지 않고 `not configured`를 표시한다.
5. 필수 CI 작업은 조건부로 건너뛰지 않고 항상 실행되게 한다.
6. 캐시는 속도 최적화일 뿐 정확성의 전제가 아니다.
7. 값 누락, 예상하지 못한 상태, 조건 판별 실패와 명령 실패는 fail-closed로 처리한다.
8. CI/CD 파일 변경은 높은 위험이며 사람 확인 없이는 자동 수정·병합하지 않는다.

## Codex self-review와 사람 확인

- 모든 구현은 커밋 전에 기준 브랜치부터 작업 트리까지의 전체 diff를 Codex가 다시 검토한다.
- self-review 항목과 수정·재검증 절차는 `.ai/policies/review-automation.md`를 따른다.
- self-review는 예방적 품질 점검이며 실제 버그나 검증 실패가 발생한 뒤 적용하는 `.ai/policies/debugging.md`의 원인 분석을 대체하지 않는다.
- 문제가 발견되면 수정하고 현재 변경 전체를 다시 self-review한 뒤 위험도에 맞는 로컬 검증을 처음부터 다시 수행한다.
- GitHub Codex 별도 리뷰는 사용하지 않는다. self-review 결과, CI와 사람 확인 여부를 PR에 구분해 기록한다.
- 높은 위험 변경은 self-review와 CI 통과만으로 병합하지 않고 사람 확인을 필수로 한다.
- 낮음·중간 위험도 auto-merge 가능 여부는 `.ai/policies/review-automation.md`의 fail-closed 조건을 모두 충족할 때만 판단한다.

## 반복 수정과 범위 분리

- 수정과 재검증이 반복되어 새로운 문제가 계속 생기면 `.ai/policies/debugging.md`의 반복 실패 기준에 따라 자동 수정을 중단하고 사용자와 범위 분리 또는 재설계를 검토한다.
- 반복 횟수에 도달했다는 이유로 병합하지 않는다. 미해결 차단 문제는 백로그로 옮겨도 병합 조건을 충족하지 못한다.
- 안전한 부분만 분리하더라도 그 변경 자체의 필수 CI와 필요한 리뷰를 다시 통과해야 한다. 남은 작업은 별도 Issue·PR로 관리한다.

> 절차 설계 참고: [Superpowers의 verification-before-completion](https://github.com/obra/superpowers/tree/main/skills/verification-before-completion)을 현재 위험도 기반 정책에 맞게 재구성했다.

## 완료 조건

- 요청한 기능과 완료 조건 충족
- 위험도에 맞는 로컬 검증 수행
- 구성된 CI 통과
- 높은 위험이면 사람 확인 완료
- 알려진 문제와 백로그 이관 내용 기록
- auto-merge 정책 판정과 필요한 사람 확인 완료
